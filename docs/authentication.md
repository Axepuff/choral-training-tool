# Вход и права доступа

Согласованная схема; backend авторизации реализован в Issue #4,
операторские команды и настройки — в [backend.md](backend.md#авторизация-issue-4). На старте два аккаунта:
преподаватель и администратор. Это две роли, а не отдельные способы входа.

## Доступ

| Действие | Участник по ссылке | Преподаватель | Администратор |
| --- | --- | --- | --- |
| Открывать опубликованный список песен | Да, только просмотр | Да | Да |
| Слушать опубликованную песню | Да | Да | Да |
| Менять громкость, Solo/Mute, позицию | Локально | Локально | Локально |
| Создавать песни | Нет | Да | Да |
| Изменять/удалять песни, управлять ссылками | Нет | Свои | Все |
| Создавать/блокировать аккаунты, менять роли | Нет | Нет | Да |

Публичные ссылки открывают список песен или отдельный плеер без регистрации.
Список называется «Песни» во всех режимах. Гость видит опубликованные песни,
поиск и сортировку, может открыть плеер, но не создавать и не редактировать.
Преподаватель видит свои песни (в том числе ещё не опубликованные) и доступные
публичные, редактирует только свои. Администратор видит и редактирует все песни.
Преподаватель и администратор копируют ссылку на список из его заголовка;
она открывает гостевой режим. У гостя этой кнопки нет.

Будущий backend использует случайные непредсказуемые токены с явной областью:
одна песня или опубликованный список. Токен списка даёт доступ только к
опубликованным в нём песням и аудио для воспроизведения. Черновики, приватные записи
и полномочия редактирования по нему недоступны. Ссылку можно
переслать; это не приватный доступ конкретного человека. Преподаватель-владелец
или администратор может отключить ссылку или перевыпустить её. После перевыпуска
старая перестаёт работать. Отключение не может отозвать уже загруженные браузером
аудиоданные. Прямого скачивания оригиналов нет: они удаляются после успешной
конвертации; воспроизводимое аудио браузер всё равно получает.

## Аутентификация на Go

- Одна форма: email + пароль. Публичной регистрации и переключателя ролей нет.
  Аккаунты создаёт администратор, роль возвращает сервер после входа.
- Сервер проверяет пароль по хешу Argon2id с уникальной солью. Пароли и секреты
  не помещаются в исходники, URL, журналы или браузерное хранилище.
- После входа — случайный непрозрачный идентификатор серверной сессии в cookie
  `HttpOnly; Secure; SameSite=Lax; Path=/`, только HTTPS. Сессия ротируется при входе,
  отзывается при выходе, блокировке аккаунта и сбросе пароля. Абсолютный срок действия — 7 суток без продления. Frontend и API размещаем на одном origin.
- Сервер проверяет роль и владельца песни в каждом запросе. Публичные токены
  не принимаются как полномочия редактирования. Изменяющие запросы защищаются от CSRF.
- Неверный email и неверный пароль дают одинаковое сообщение. Ограничение попыток
  входа реализуется на сервере: один login одновременно без очереди, общий
  устойчивый бюджет 20 проверок/минуту и прежний лимит пары IP/email. Argon2id
  не удерживает БД; перед созданием сессии повторно сверяется состояние аккаунта.
  Лимиты и ответы — [API](api/README.md#сессии-csrf-и-аккаунты). Сетевую ошибку можно повторить без смены данных.
- На первом этапе пароль восстанавливается через администратора, без отдельного
  email-сервиса. Администратор передаёт начальные/временные пароли вне приложения;
  первого админа создаёт CLI bootstrap, учителя — create-teacher. Временный пароль
  обязательно меняется через PUT /auth/password, все сессии отзываются. Для
  восстановления единственного admin существует локальная команда reset-admin.

## UI сейчас

`/?page=sign-in` и «Страницы → Вход» в Storybook. Семь stories: обычный и мобильный
вид, проверка данных, неверные данные, ошибка соединения, успешный ответ и отсутствие
backend. Обычная страница не отправляет email/пароль и сообщает, что вход не подключён.
Интерактивные stories используют вымышленные данные и мок-функции. UI пока не использует реальные аккаунты, сессии и серверное разграничение прав;
переход в библиотеку после входа подключается в #9. Доступность страниц по
query-параметру сейчас служит навигацией между макетами и не является защитой доступа.

## Список и редактирование сейчас

`/?page=library` открывает гостевой список; `&list=choir-demo` — стабильная демо-ссылка
на тот же список. Параметр пока не является токеном доступа. В Storybook преподаватель,
администратор и гость представлены отдельными stories; гостевой режим выбран
по умолчанию в приложении. Роль не задаётся публичной ссылкой или query-параметром.
Режим редактирования использует ту же форму, что создание; существующие аудиофайлы
представлены именами-заглушками. Изменения и выбранные замены сохраняются только
в памяти компонента и сбрасываются при перезагрузке/переходе на другую страницу.
Серверного сохранения, реальной обработки файлов и проверки токенов пока нет.
На GitHub Pages макет приложения опубликован под `/app/`, а Storybook — в корне.
Это позволяет открыть скопированную гостевую ссылку без интерфейса Storybook.

## Интеграция songs (Issue #5)

Session API песен использует реальный Authenticate с CSRF/password gate, затем
authorizer. Teacher не получает чужой draft даже по ID (404); published/ready
может прочитать, но изменение даёт 403. Admin управляет всеми. Owner назначается
по сессии, role/owner из запроса не принимаются. В write-транзакции повторно
проверяются сессия, актуальная роль, блокировка и owner. Гостевых endpoints пока
нет: они остаются #6. Frontend-макеты ещё не подключены к этому API.

## Реализация sharing (Issue #6)

Публичные song/list токены теперь проверяются сервером в `internal/sharing`.
Область списка — опубликованные готовые песни одного owner; cookie-сессия не
расширяет public grant. Owner/admin создаёт, отключает и перевыпускает независимые
ссылки, с проверкой CSRF и live identity в транзакции. Метаданные и media используют
единый published/ready scope; оригиналы не выдаются. Отзыв действует на новые
запросы и не удаляет уже полученные байты. Media до #7/#8 проверяется через
Storage fixtures; без адаптера сервер возвращает 503. Детали и границы —
[backend.md](backend.md#публичные-ссылки-и-media-issue-6). UI остаётся макетом до #10.

## Upload и jobs (Issue #7)

Upload использует серверную session/CSRF и проверяет owner/admin до чтения тела и
повторно перед commit (включая live-сессию, актуальную роль, блокировку и version).
Public token не даёт права загрузки или чтения job. Job доступен owner/admin;
приватная чужая песня и её jobs скрываются 404. Originals лежат за Storage и
никогда не выдаются media endpoint. Подробнее: [backend.md](backend.md#загрузка-и-приватное-хранилище-issue-7).

## Frontend интеграция (Issue #9)

Разделы «UI сейчас» и «Список и редактирование сейчас» выше описывают исторический
макет. Runtime SignIn теперь отправляет реальные credentials в Go API;
me восстанавливает сессию, 401 снимает права, logout отзывает сессию, temporary
password открывает смену пароля. Query-параметр не задаёт роль; public routes
всегда guest и не отправляют session cookie. Pages/Storybook остаются явным demo.
Личные songs/forms остаются #10; вместо фиктивного успеха runtime сообщает о
неподключённой функции. Детали: [frontend-auth.md](frontend-auth.md).

## Песни и ссылки в runtime (Issue #10)

Историческое описание макетов выше заменено реальной интеграцией: список, формы,
upload/jobs и sharing используют session/CSRF; права выводятся из серверных
role/owner ID и перепроверяются API. Guest routes остаются read-only без cookie.
Временная ошибка фонового me сохраняет форму и показывает ошибку; 401 снимает
сессию. Подробнее: [frontend-songs.md](frontend-songs.md).
