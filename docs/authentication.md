# Вход и права доступа

Согласованная схема; backend пока не реализован. На старте два аккаунта:
преподаватель и администратор. Это две роли, а не отдельные способы входа.

## Доступ

| Действие | Участник по ссылке | Преподаватель | Администратор |
| --- | --- | --- | --- |
| Слушать опубликованную песню | Да | Да | Да |
| Менять громкость, Solo/Mute, позицию | Локально | Локально | Локально |
| Создавать песни | Нет | Да | Да |
| Изменять/удалять песни, управлять ссылками | Нет | Свои | Все |
| Создавать/блокировать аккаунты, менять роли | Нет | Нет | Да |

Публичная ссылка открывает сразу плеер без регистрации. Случайный непредсказуемый
токен даёт доступ только к одной песне и её аудио для воспроизведения. Ссылку можно
переслать; это не приватный доступ конкретного человека. Преподаватель-владелец
или администратор может отключить ссылку или перевыпустить её. После перевыпуска
старая перестаёт работать. Отключение не может отозвать уже загруженные браузером
аудиоданные. Прямого скачивания оригиналов нет: они удаляются после успешной
конвертации; воспроизводимое аудио браузер всё равно получает.

## Аутентификация на Go (план)

- Одна форма: email + пароль. Публичной регистрации и переключателя ролей нет.
  Аккаунты создаёт администратор, роль возвращает сервер после входа.
- Сервер проверяет пароль по хешу Argon2id с уникальной солью. Пароли и секреты
  не помещаются в исходники, URL, журналы или браузерное хранилище.
- После входа — случайный непрозрачный идентификатор серверной сессии в cookie
  `HttpOnly; Secure; SameSite=Lax; Path=/`, только HTTPS. Сессия ротируется при входе,
  отзывается при выходе, блокировке аккаунта и сбросе пароля. Срок действия определим
  при реализации backend. Frontend и API размещаем на одном origin.
- Сервер проверяет роль и владельца песни в каждом запросе. Публичные токены
  не принимаются как полномочия редактирования. Изменяющие запросы защищаются от CSRF.
- Неверный email и неверный пароль дают одинаковое сообщение. Ограничение попыток
  входа реализуется на сервере. Сетевую ошибку можно повторить без смены данных.
- На первом этапе пароль восстанавливается через администратора, без отдельного
  email-сервиса. Администратор передаёт начальные/временные пароли вне приложения;
  способ первоначального создания админа и смены временного пароля определим
  при реализации backend.

## UI сейчас

`/?page=sign-in` и «Страницы → Вход» в Storybook. Семь stories: обычный и мобильный
вид, проверка данных, неверные данные, ошибка соединения, успешный ответ и отсутствие
backend. Обычная страница не отправляет email/пароль и сообщает, что вход не подключён.
Интерактивные stories используют вымышленные данные и мок-функции. Реальных аккаунтов,
сессий, разграничения прав и перехода в библиотеку пока нет. Доступность страниц по
query-параметру сейчас служит навигацией между макетами и не является защитой доступа.
