# Синхронный плеер — Issue #11

Runtime public song/list, название песни в личном списке и «Слушать песню» в сохранённой песне используют настоящие
media URLs, gain, BPM/размер, durationMs и peaks из Go API. Историческое описание
мок-плеера в handoff относится к этапу дизайна. Stories/Pages demo сохраняют явно
демонстрационный таймер; runtime на него при ошибках не переключается.

## Движок и границы

`src/audio/engine.ts` использует браузерный Web Audio без новых зависимостей.
Один AudioContext 48 kHz и общий scheduled start для всех дорожек. Каждая дорожка
поступает окнами до 4 секунд; следующие окна планируются заранее на том же clock,
без перезапуска часов на границах. Pause сохраняет позицию context.currentTime,
seek/resume запрашивают окно от новой позиции. RAF только читает audio clock для
курсора. После конца короткой дорожки — тишина. Gain каждой дорожки меняется с
коротким сглаживанием; Solo/Mute взаимоисключаются, все Solo сбрасываются.
`updateMix` не меняет входные объекты; применение gain выполняется после React
commit, вне state updater. Повтор updater в StrictMode даёт тот же результат.

Загрузка индексов последовательная; кнопка старта ждёт попыток всех дорожек.
Ошибка файла не блокирует остальные дорожки, ошибка peaks не блокирует звук.
Для повтора неудачной загрузки обновите страницу. Число дорожек 1–32 и произвольные
ID задаёт серверный контракт. Общая сетка учитывает знаменатель размера и
фактическую длительность; короткая волна не растягивается до конца песни.
Микшер и таймлайн прокручиваются внутри своих областей, не растягивая страницу.

### Загрузка с ограниченной памятью

`src/audio/mp4.ts` читает индекс серверного AAC-LC mono 48 kHz MP4 через Range,
пропуская `mdat` по размеру box. В памяти остаются индекс и короткие окна PCM;
20-минутный файл целиком не скачивается и не декодируется. Это адаптер конкретного
выхода существующего FFmpeg worker, не универсальный MP4 demuxer: используются
нефрагментированный контейнер, один непрерывный audio stream, `stco`, AAC frames
по 1024 samples и начальный edit для encoder delay. Несовместимый индекс даёт
видимую ошибку. Серверная конвертация и формат playback не изменены.

Для окна собирается небольшой MP4 с исходным sample description и пересчитанными
sample/chunk tables. Браузер декодирует AAC своим `decodeAudioData`; два предыдущих
AAC frame восстанавливают overlap перед слышимым началом. Encoder delay учитывается
в sample offsets. Окно обрезается по sample, а не таймером. Это позволяет сохранить
точное общее планирование без независимых HTMLMediaElement clocks и без новой
библиотеки/AudioWorklet/WebCodecs (и их дополнительных требований совместимости).

Горизонт планирования — менее 12 секунд, окна до 4 секунд. Для 32 mono 48 kHz
дорожек запланированный PCM занимает до 73 728 000 bytes (70.3125 MiB), независимо
от общей длины. Кроме него существуют индекс, загружаемое окно, временный PCM
декодера, peaks и память браузера; это не ограничение общего RSS процесса.
Лимит суммарной длины/PCM 256 MiB удалён: 32 дорожки по 20 минут поддерживаются
тем же оконным путём. Индекс ограничен 2 MiB на файл, что выше индекса максимального
серверного fixture. Завершившиеся nodes отключаются и освобождают buffer.
Одновременные seek не накапливают декодирование: новый запуск ждёт завершения
предыдущего запроса, затем проверяет generation. Если новое окно не успевает к
назначенному времени, независимая проверка audio clock (каждые 50 ms) останавливает весь транспорт останавливается на границе последнего
загруженного окна с видимой ошибкой; возобновление требует нажатия Play.
Курсор ограничен этой границей даже до срабатывания проверки. Проверка не ждёт
завершения fetch/decode, а поздний результат не запускает транспорт снова.
Намерение воспроизведения хранится отдельно от playing: последний из серии seek
возобновляет звук, явная pause/dispose отменяет это намерение.

Каждый запрос требует 206 с корректным Content-Range; ETag закрепляется при чтении
индекса. Изменившийся ETag, неполное тело, 404/отзыв или неподдержанный Range дают
ошибку дорожки вместо смешивания байтов старого и нового asset. Уже запланированные
окна этой дорожки могут доиграть; новые не добавляются. Исключённая дорожка больше
не участвует в определении активного Solo: gain исправных дорожек восстанавливается
сразу, а её заблокированная кнопка Solo отображается выключенной. Это сохраняется
и при повторном применении старого mix из UI.

Resume вызывается из кнопки до await; autoplay не используется. При блокировке
аудиоустройства показывается ошибка, можно нажать Play снова. Уход страницы в фон,
pagehide и unmount останавливают звук; unmount отменяет fetch, закрывает контекст,
освобождает buffers и connections. Поздний resume/decode после ухода не запускает
прошлую песню. Public media/peaks запросы отправляются с credentials=omit, session —
same-origin; redirect запрещён, URLs ограничены `/api/v1/`. Отзыв ссылки даёт ошибку
на новом запросе; уже загруженные байты отозвать нельзя.

Повтор и метроном runtime пока заблокированы с объясняющими title. Выбор диапазона,
реальный loop scheduling и метроном — #12. Демо фиксированных тактов 2–3 не выдаётся
за готовый runtime loop.

## Воспроизводимые проверки

```sh
node --test tests/audio.test.mjs
node tests/audio-browser.mjs
```

Первый набор (12 поведенческих тестов) использует управляемый clock: 32 стабильных
ID, 20 циклов pause/resume/seek, короткий файл, gain/solo/mute, неизменность и
повторяемость all-solo reset, dispose и гонки resume/decode/unmount. Отдельный тест
проходит все 300 четырёхсекундных окон 20-минутной песни для 32 дорожек: старт
каждого окна равен исходному epoch + offset, одновременно удерживаются не более
трёх окон. Проверяется общая остановка при starvation. Это детерминированное
моделирование clock, а не двадцатиминутное прослушивание.
Регрессии ревью дополнительно проверяют перекрывающиеся seek с задержанным decode,
явную pause во время seek, зависший запрос следующего окна без ответа и ошибку
Solo-дорожки при загрузке следующего окна с восстановлением gain исправной дорожки.

Браузерный тест запускает Vite и headless Google Chrome через CDP; нужны
`/usr/bin/google-chrome` и `ffmpeg`. Синтетические файлы создаются вне Git,
конвертируются в настоящие AAC-LC mono 48 kHz 96 kbit/s и отдаются контрактным
fixture API с Range/ETag. Проверяются:

- 32 канала с отдельным 404, настоящие peaks, public requests без cookies
  при существующей синтетической cookie; смена ETag одной дорожки и отзыв всех
  media после успешного воспроизведения; снятие Solo у дорожки с ошибкой ETag;
- trusted mouse gesture при включённой autoplay policy, cursor/pause/seek/resume,
  смена песни и закрытие старого AudioContext;
- побитовое совпадение оконного и полного decode на 8-секундном fixture, включая
  дробный seek и границы AAC frames; OfflineAudioContext проверяет точный общий
  старт и сложение сигналов;
- 32 настоящих **20-минутных** файла, Range-only загрузка, seek/resume на 600.123,
  1196, 3.5 и 1198 секундах; сброс всех Solo через реальный React StrictMode;
- синхронные старты последующих окон без накопления сдвига, ограниченный объём
  запланированного PCM; отсутствие переполнения короткой и длинной песни при
  320×640, 360×740, 740×360 и 1280×800.

Обычный запуск проверяет 12.5 секунд непрерывного звука; длительность можно увеличить:

```sh
CHORAL_AUDIO_SECONDS=60 node tests/audio-browser.mjs
```

В предыдущем проходе проверен Linux Google Chrome **147.0.7727.116 headless**,
FFmpeg **6.1.1**, 60 секунд непрерывного транспорта 32 дорожек. Пиковый объём
запланированного PCM — **73 728 000 bytes**, самый большой Range — **225 863 bytes**
(индекс); все повторные seek/resume прошли. Полные 20 минут непрерывного реального
воспроизведения и аппаратный audio output не проверялись. Fixture API существует
только в тесте; runtime требует настоящий Go backend.

### Незакрытая мобильная проверка (замечание P2 ревью)

Safari/iOS и Chrome/Android на физических устройствах в этой среде недоступны.
Эмуляция viewport на Linux не проверяет mobile gesture/autoplay, системное
interruption/background и повторный запуск аудиоустройства. Это **блокер полной
приёмки Issue #11**, а не пройденный mobile smoke. Перед приёмкой записать версии
ОС/браузера, модель устройства и результаты: первый Play жестом, отказ autoplay,
20-минутная песня с 32 дорожками, несколько seek/pause/resume, смена песни,
уход в фон/возврат и interruption с последующим явным Play. Здесь эти результаты
не заявляются и не заменяются моками.
