# Синхронный плеер — Issue #11

Runtime public song/list, название песни в личном списке и «Слушать песню» в сохранённой песне используют настоящие
media URLs, gain, BPM/размер, durationMs и peaks из Go API. Историческое описание
мок-плеера в handoff относится к этапу дизайна. Stories/Pages demo сохраняют явно
демонстрационный таймер; runtime на него при ошибках не переключается.

## Движок и границы

`src/audio/engine.ts` использует браузерный Web Audio без новых зависимостей.
Один AudioContext 48 kHz и общий scheduled start для всех дорожек. Каждая дорожка
поступает окнами до 4 секунд; следующие окна планируются заранее на том же clock,
без перезапуска часов на границах. Pause сохраняет позицию context.currentTime,
seek/resume запрашивают окно от новой позиции. RAF только читает audio clock для
курсора. После конца короткой дорожки — тишина. Gain каждой дорожки меняется с
коротким сглаживанием; Solo/Mute взаимоисключаются, все Solo сбрасываются.
`updateMix` не меняет входные объекты; применение gain выполняется после React
commit, вне state updater. Повтор updater в StrictMode даёт тот же результат.

Загрузка индексов последовательная; кнопка старта ждёт попыток всех дорожек.
Ошибка файла не блокирует остальные дорожки, ошибка peaks не блокирует звук.
Для повтора неудачной загрузки обновите страницу. Число дорожек 1–32 и произвольные
ID задаёт серверный контракт. Общая сетка учитывает знаменатель размера и
фактическую длительность; короткая волна не растягивается до конца песни.
Микшер и таймлайн прокручиваются внутри своих областей, не растягивая страницу.

### Загрузка с ограниченной памятью

`src/audio/mp4.ts` читает индекс серверного AAC-LC mono 48 kHz MP4 через Range,
пропуская `mdat` по размеру box. В памяти остаются индекс и короткие окна PCM;
20-минутный файл целиком не скачивается и не декодируется. Это адаптер конкретного
выхода существующего FFmpeg worker, не универсальный MP4 demuxer: используются
нефрагментированный контейнер, один непрерывный audio stream, `stco`, AAC frames
по 1024 samples и начальный edit для encoder delay. Несовместимый индекс даёт
видимую ошибку. Серверная конвертация и формат playback не изменены.

Контейнерные timestamps `stts` могут отличаться от 1024 на несколько ticks:
`asetpts=N/SR/TB` и resampling входного WAV 44,1 kHz дают 1023/1025, а 8 kHz —
1018/1030. Это округление timestamps, не переменная длина AAC frames. Reader
проверяет число frames, целостность таблицы и суммарное отклонение не более
48 samples (1 ms), включая runs перед последним frame. Устойчивый дрейф и
разрывы не принимаются. PCM адресуется по фиксированным AAC frames, поэтому
округление не накапливается при проигрывании и seek. Уже созданные сервером
assets читаются этим же путём; повторная загрузка WAV для исправления не нужна.

При наличии `AudioDecoder`/`EncodedAudioChunk` и положительном результате
`AudioDecoder.isConfigSupported` reader передаёт исходные AAC-пакеты в WebCodecs.
AudioSpecificConfig задаёт контрактный AAC-LC mono 48 kHz; timestamps/durations
отсчитываются по 1024 samples, без повторного MP4 demux в `decodeAudioData`.
Проверяются rate, channels, непрерывность output timestamps и число samples.
Один module Worker на AudioContext принимает окна разных дорожек и передаёт
готовый PCM через transferable ArrayBuffer. `flush` завершает окно; все AudioData
и decoder закрываются после использования/при ошибке, закрытие AudioContext
завершает worker и отклоняет его ожидающие запросы. Это не даёт тысячам callback
от AAC frames конкурировать с интерфейсом на основном потоке: такой вариант
останавливался на buffered boundary в проверке 32 дорожек и не принят.
Два предыдущих AAC frame восстанавливают overlap; исходный encoder delay
применяется один раз при извлечении PCM.

Визуальная позиция читается из audio clock с частотой до 20 Hz; сам scheduling
от неё не зависит. Геометрия волн кешируется по immutable peaks response и не
пересчитывается при Solo/Mute; сетка тактов тоже переиспользуется. CSS-позиция
курсора меняется на самом курсоре, без смены наследуемой переменной всей сетки.

Для браузера без поддержанного AAC WebCodecs остаётся `decodeAudioData` с небольшим
пересчитанным MP4. Этот fallback сохраняет проверку длины: на проверенном iPhone
он возвращал PCM на 2112 samples короче даже с явным нулевым edit, поэтому там
нужен пакетный путь. Наличие API не гарантирует поддержку кодека; это проверяется
в самом браузере. Согласно [MDN BCD](https://github.com/mdn/browser-compat-data/blob/main/api/AudioDecoder.json),
Safari поддерживает AudioDecoder начиная с 26. Работа на более старых Safari
не заявляется. Дополнительных зависимостей или смены серверного формата нет.

Горизонт планирования — менее 12 секунд, окна до 4 секунд. Для 32 mono 48 kHz
дорожек запланированный PCM занимает до 73 728 000 bytes (70.3125 MiB), независимо
от общей длины. Кроме него существуют индекс, загружаемое окно, временный PCM
декодера, peaks и память браузера; это не ограничение общего RSS процесса.
Лимит суммарной длины/PCM 256 MiB удалён: 32 дорожки по 20 минут поддерживаются
тем же оконным путём. Индекс ограничен 2 MiB на файл, что выше индекса максимального
серверного fixture. Завершившиеся nodes отключаются и освобождают buffer.
Одновременные seek не накапливают декодирование: новый запуск ждёт завершения
предыдущего запроса, затем проверяет generation. Если новое окно не успевает к
назначенному времени, независимая проверка audio clock (каждые 50 ms) останавливает весь транспорт останавливается на границе последнего
загруженного окна с видимой ошибкой; возобновление требует нажатия Play.
Курсор ограничен этой границей даже до срабатывания проверки. Проверка не ждёт
завершения fetch/decode, а поздний результат не запускает транспорт снова.
Намерение воспроизведения хранится отдельно от playing: последний из серии seek
возобновляет звук, явная pause/dispose отменяет это намерение.
По решению владельца Play/Pause заблокирована нативным `disabled` при загрузке
индексов, ожидании первого окна и возобновлении после seek. Отображаются значок
Play, «Загрузка аудио…» и `aria-busy`; кнопка визуально приглушена. Повторное
нажатие не запускает новую загрузку и не отменяет ожидающий запуск. Обработчик
также проверяет намерение движка до обновления UI. После готовности снова доступна
пауза; после ошибки — повторный Play. Фоновая подгрузка следующих окон во время
звучания не блокирует Pause. Уход со страницы/в фон по-прежнему отменяет запуск,
поэтому поздний fetch/decode не включает остановленную песню.

Каждый запрос требует 206 с корректным Content-Range; ETag закрепляется при чтении
индекса. Изменившийся ETag, неполное тело, 404/отзыв или неподдержанный Range дают
ошибку дорожки вместо смешивания байтов старого и нового asset. Уже запланированные
окна этой дорожки могут доиграть; новые не добавляются. Исключённая дорожка больше
не участвует в определении активного Solo: gain исправных дорожек восстанавливается
сразу, а её заблокированная кнопка Solo отображается выключенной. Это сохраняется
и при повторном применении старого mix из UI.

Если очередное окно не удалось загрузить ни у одной из дорожек, у которых
в этом окне ещё должен быть звук, движок останавливает весь транспорт и показывает
«Нет доступных дорожек. Воспроизведение остановлено.». Курсор остаётся на текущей
позиции, не дальше конца реально запланированного аудио; это ограничение сохраняется
и после исключения последнего stream. Таймеры и запланированные nodes освобождаются.
Ошибка одной партии не останавливает исправные, а естественное окончание коротких
дорожек не считается сетевым отказом.

Resume вызывается из кнопки до await; autoplay не используется. При блокировке
аудиоустройства показывается ошибка, можно нажать Play снова. Уход страницы в фон,
pagehide и unmount останавливают звук; unmount отменяет fetch, закрывает контекст,
освобождает buffers и connections. Поздний resume/decode после ухода не запускает
прошлую песню. Public media/peaks запросы отправляются с credentials=omit, session —
same-origin; redirect запрещён, URLs ограничены `/api/v1/`. Отзыв ссылки даёт ошибку
на новом запросе; уже загруженные байты отозвать нельзя.

Инициализация имеет отдельное состояние загрузки: отсутствие записи в словаре
дорожек не означает бесконечное ожидание. Если конструктор AudioContext бросает
исключение, все дорожки получают «Аудиоустройство недоступно», загрузка завершается,
а основная кнопка доступна с названием «Повторить подключение аудио» и
`aria-busy=false`. Нажатие повторяет инициализацию и чтение индексов без перезагрузки
страницы; повторный отказ снова оставляет доступную кнопку и сообщение об ошибке.
После успешного подключения звук запускается отдельным явным Play. Последний
ожидающий peaks-ответ не блокирует Play, если аудиоиндексы уже готовы.

Повтор и метроном runtime пока заблокированы с объясняющими title. Выбор диапазона,
реальный loop scheduling и метроном — #12. Демо фиксированных тактов 2–3 не выдаётся
за готовый runtime loop.

## Воспроизводимые проверки

```sh
node --test tests/audio.test.mjs
npm run test:audio
node tests/audio-browser.mjs
```

Первый набор (12 поведенческих тестов) использует управляемый clock: 32 стабильных
ID, 20 циклов pause/resume/seek, короткий файл, gain/solo/mute, неизменность и
повторяемость all-solo reset, dispose и гонки resume/decode/unmount. Отдельный тест
проходит все 300 четырёхсекундных окон 20-минутной песни для 32 дорожек: старт
каждого окна равен исходному epoch + offset, одновременно удерживаются не более
трёх окон. Проверяется общая остановка при starvation. Это детерминированное
моделирование clock, а не двадцатиминутное прослушивание.
Регрессии ревью дополнительно проверяют перекрывающиеся seek с задержанным decode,
явную pause во время seek, зависший запрос следующего окна без ответа и ошибку
Solo-дорожки при загрузке следующего окна с восстановлением gain исправной дорожки.

`npm run test:audio` дополнительно проверяет reader на настоящих stereo WAV
8/11,025/16/22,05/32/44,1/48/88,2/96 kHz, преобразованных командой FFmpeg с теми
же аудиопараметрами и timestamp filter, что в worker. Проверяются повреждённые
таблицы, счётчики и накопленный дрейф; тесты включены в frontend PR checks.

Браузерный тест запускает Vite и headless Google Chrome через CDP; нужны
`/usr/bin/google-chrome` и `ffmpeg`. Для другого Chromium-based binary задайте
`CHORAL_CHROME_BIN=/usr/bin/chromium`. Синтетические файлы создаются вне Git,
конвертируются в настоящие AAC-LC mono 48 kHz 96 kbit/s и отдаются контрактным
fixture API с Range/ETag. Короткий WAV и длинный sine имеют исходную частоту
44,1 kHz и проходят серверный `asetpts`, чтобы воспроизводить реальное
округление `stts`, пропущенное первоначальными fixtures. Проверяются:

- 32 канала с отдельным 404, настоящие peaks, public requests без cookies
  при существующей синтетической cookie; смена ETag одной дорожки и отзыв всех
  media после успешного воспроизведения; снятие Solo у дорожки с ошибкой ETag;
- trusted mouse gesture при включённой autoplay policy, cursor/pause/seek/resume,
  смена песни и закрытие старого AudioContext;
- сравнение оконного и полного decode на 8-секундном fixture (максимальная разница
  амплитуд <0,001), включая дробный seek и границы AAC frames; OfflineAudioContext проверяет точный общий
  старт и сложение сигналов;
- 32 настоящих **20-минутных** файла, Range-only загрузка, seek/resume на 600.123,
  1196, 3.5 и 1198 секундах; сброс всех Solo через реальный React StrictMode;
- синхронные старты последующих окон без накопления сдвига, ограниченный объём
  запланированного PCM; отсутствие переполнения короткой и длинной песни при
  320×640, 360×740, 740×360 и 1280×800.

Обычный запуск проверяет 12.5 секунд непрерывного звука; длительность можно увеличить:

```sh
CHORAL_AUDIO_SECONDS=60 node tests/audio-browser.mjs
```

В предыдущем проходе проверен Linux Google Chrome **147.0.7727.116 headless**,
FFmpeg **6.1.1**, 60 секунд непрерывного транспорта 32 дорожек. Пиковый объём
запланированного PCM — **73 728 000 bytes**, самый большой Range — **225 863 bytes**
(индекс); все повторные seek/resume прошли. Полные 20 минут непрерывного реального
воспроизведения и аппаратный audio output не проверялись. Fixture API существует
только в тесте; runtime требует настоящий Go backend.

### Обнаруженный блокер Safari и диагностика

Владелец подтвердил iPhone 16 / iOS 26.6.2 / Safari: после исправления timestamps
волны отображаются, но первый Play даёт «Неподдерживаемый декодер AAC».
Само наличие индекса/peaks и статуса «Готово» не доказывает успешное decode.

В dev-режиме ошибки `AAC_SAMPLE_RATE`, `AAC_SHORT_PCM`, `AAC_EMPTY_WINDOW`
сохраняют фактические размеры/rate декодированного AudioBuffer. Раскрываемая
диагностика под транспортом помогает получить данные с iPhone без Safari
Web Inspector. В production интерфейс её не показывает. Короткий/неверный PCM
по-прежнему отклоняется: диагностика не дополняет его тишиной и не меняет timing.
Браузерный regression намеренно укорачивает настоящий результат decode и
проверяет доступность чисел на странице; это моделирование формы ошибки,
не воспроизведение CoreAudio и не подтверждение работоспособности Safari.
Диагностический набор прошёл локально: 31 audio test, lint/typecheck, сборки
приложения/Storybook, assemble-pages и полный браузерный сценарий, включая
отображение отчёта для всех завершившихся decode failures.

### Явное описание priming для коротких AAC-окон

Диагностика с физического iPhone: `AAC_SHORT_PCM`, encoded 194560, decoded 192448,
context/decoded rate 48000, offset 1024, required 192000 для окна 0–4 секунды.
Разница — 2112 samples. Это согласуется с неявным AAC priming в AVFoundation:
собранный reader MP4 не содержал edit list, но сохранял sample groups полной песни.

Каждое окно теперь содержит явный edit с media time 0 и длительностью всех
закодированных samples. `mvhd`, `tkhd`, `mdhd` используют точные длительности
в timebase 48000; группы `sgpd`/`sbgp` и `udta` полной записи не копируются.
Так контейнер описывает полное окно пакетов, а исходный priming применяется
ровно один раз при извлечении нужного PCM. Проверка длины сохраняется, отсутствующий
звук не заменяется тишиной. Изменяется только frontend; существующие файлы
перекодировать или загружать заново не требуется.

Регрессия моделирует неявный срез 2112 при отсутствии edit list; на прежнем reader
она давала те же числа, что отчёт устройства. Это модель, не запуск CoreAudio.
После изменения прошли 32 аудиотеста, lint/typecheck, обе сборки и assemble-pages.
Настоящий decode в Linux Chromium 154.0.8037.57 / FFmpeg 7.1.5 проверен сравнением
семи окон с полным decode: начало, дробный seek, стык 4 секунд и последние 50 ms,
max amplitude difference 0,000122. Полный браузерный сценарий прошёл, включая
12,5 секунды непрерывного транспорта 32 потоков из 20-минутного AAC fixture,
повторные seek/resume, PCM bound 73 728 000 bytes и dev-диагностику ошибок.
Последующая повторная проверка владельцем на физическом Safari/iPhone дала
**те же** значения 194560 → 192448 и ошибку `AAC_SHORT_PCM`. Исправление metadata
само по себе проблему не решило; модель priming policy не описывала поведение
реального декодера. Нулевой edit не считается подтверждённым исправлением Safari.

### Пакетное декодирование после повторного отказа Safari

Reader предпочитает поддержанный AAC WebCodecs, минуя проблемный MP4 decode.
Если декодер отвергает данные, меняет timestamps/формат или возвращает неполный
PCM, дорожка получает ошибку; обхода проверок и добавления тишины нет.
Dev-диагностика содержит `readerVersion: 2`, выбранный `decoder` и, для ошибки
пакетного пути, `packetFailure`. Это позволяет отличить старый JS в кеше от
нового пути и увидеть причину отказа. Данных файла и учётных данных в отчёте нет.
Общее сообщение изменено на «Не удалось декодировать аудиофрагмент»: ошибка
обработки окна не объявляется отсутствием поддержки AAC в браузере.

Unit-проверки покрывают обход `decodeAudioData`, начало/seek/tail, codec errors,
разрыв timestamp, неполный PCM, неподдержанный config и закрытие decoder при pending
flush. Отдельно проверяются ответы worker вне очереди, отклонение его pending
запросов и отсутствие нового worker после закрытия контекста.
Браузерный сценарий сравнивает настоящий WebCodecs и fallback с полным decode,
затем выполняет UI-воспроизведение при намеренно отключённом `decodeAudioData`.
Проверка запрещает создание AudioDecoder на main thread и проверяет завершение
worker после смены песни, поэтому успешный UI-прогон действительно использует worker.

Итог: 39 аудиотестов, lint/typecheck, build/build-storybook, assemble-pages и
`git diff --check` прошли. Браузерный прогон Linux Chromium 154.0.8037.57 / FFmpeg
7.1.5 проверил **60 секунд** непрерывного транспорта 32 потоков из 20-минутного
fixture при выключенном `decodeAudioData`, повторные seek/resume до конца файла,
sample comparison обоих decode paths (max amplitude difference 0,000122),
ограничение scheduled PCM 73 728 000 bytes и обработку ошибок/диагностику.
Это не проверка полного двадцатиминутного аппаратного воспроизведения и не запуск
Safari/CoreAudio в облаке. После обновления до `a22a08f` владелец сообщил
«Отлично, заработало»: воспроизведение на физическом iPhone 16 / iOS 26.6.2 /
Safari подтверждено. Последующим отчётом владелец подтвердил все семь пунктов
ручного smoke: Play, pause/resume, seek, микшер, блокировку/фон, смену песни и
