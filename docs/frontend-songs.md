# Песни, формы, загрузки и ссылки — Issue #10

Обычная сборка использует существующий Go API, SQLite и FFmpeg worker.
`LiveLibrary` подключает согласованные `SongLibrary`/`CreateSong`; fixtures остаются
только в stories и явно обозначенной Pages demo. Новых runtime-зависимостей нет.
Запуск backend и dev proxy описан в [backend.md](backend.md) и
[frontend-auth.md](frontend-auth.md).

## Поведение

- Личный список читает все страницы snapshot `/songs`, передаёт NFC/trim `q` и
  `sort=updated_desc|title_asc` серверу. При новом запросе прежний отменяется;
  loading/error/empty различаются. Ошибка имеет кнопку повтора.
- Роль и owner ID приходят из session/API, имена владельцев не угадываются.
  Teacher редактирует свои песни, admin — все, чужие опубликованные песни
  открываются только для чтения. Сервер остаётся источником авторизации:
  403/404/401 не заменяются локальным успехом. Гостевые маршруты независимы от cookie.
- Создание POST всегда создаёт draft, файлы не обязательны. PUT отправляет полную
  форму и `If-Match`. Порядок, ID и gain сохранённых дорожек удерживаются, новые
  дорожки получают ID сервера. Заметки сохраняются без trim. NFC/scalar validation:
  title 1–160, name 1–80, notes 0–1000; BPM 20–300, beats 1–32, unit 1/2/4/8/16/32.
  Нативные id/name, числовые ограничения и 44px targets сохранены.
- Созданный draft получает адрес редактирования для reload. Создание использует
  постоянный для попытки UUID idempotency key и снимок исходного тела POST.
  Если ответ потерян, повтор сначала отправляет прежнее тело с тем же ключом,
  получает ID созданного draft, затем применяет текущие поля через PUT и загружает
  выбранные файлы. Изменение формы между попытками не вызывает
  `idempotency_conflict` и не создаёт дубликат. Снимок хранится только в памяти;
  подтверждённый 400/422 позволяет исправить данные и начать новую попытку.
  При конфликте поля/файлы остаются в форме, серверная версия перечитывается.
  Повторное сохранение — явное решение пользователя записать свои поля поверх
  актуальной версии. Автоматического повторного PUT нет.
- Сохранение сначала фиксирует метаданные, затем последовательно отправляет файлы.
  Это несколько транзакций: при частичной ошибке уже сохранённые данные остаются,
  форма сохраняет выбранные файлы и показывает ошибку, а не общий успех.
  Успешно обработанные файлы повторно не отправляются при повторе этой формы.
- Multipart XHR показывает фактический upload progress. После 100% клиент ждёт
  `/jobs/{id}` до `succeeded`; queued/processing не считаются ready. Jobs после
  reload также перечитываются. При failed/probe/network error можно повторить
  сохранение либо выбрать замену. Старый active asset остаётся доступен;
  удаление выбранной замены возвращает старую дорожку, не удаляет серверный файл.
  Подтверждённый HTTP 422 probe-отказ (`corrupt_audio`, `unsupported_codec`,
  `too_long`, `probe_timeout`) завершает попытку: повтор сохранения того же
  выбранного файла получает новый Idempotency-Key. При неопределённом сетевом
  результате ключ сохраняется, чтобы повтор не создавал вторую job.
- Публикация — отдельная кнопка для **сохранённой** версии. Она не сохраняет
  незаписанные поля формы; сервер отклоняет публикацию неготовых дорожек.
  При конфликте версия перечитывается без сброса полей и выбранных файлов;
  пользователь явно повторяет публикацию актуальной сохранённой версии.
- Панель ссылок читает существующие shares, создаёт отдельные song/list ссылки,
  ротирует и отзывает их. Настоящий адрес показывается и копируется через Clipboard;
  при запрете Clipboard доступен ручной выбор адреса. GET shares не раскрывает
  старый token: для нового адреса нужно создать отдельную ссылку или заменить старую.
  Замена отключает старый token; отзыв удаляет адрес из панели. Public list показывает
  только published/ready, guest song/list открываются без входа.
- При несохранённых изменениях закрытие/reload/переход защищает стандартный
  `beforeunload` (браузер требует user activation). «Отмена» запрашивает подтверждение.
  Отмена отбрасывает только несохранённые поля; сохранённый черновик остаётся в списке.
  Файлы не записываются в localStorage/sessionStorage. Фоновая проверка сессии,
  включая временный offline, не размонтирует форму; ошибка явно показана.
  Настоящий 401 отзывает session согласно #9.

аккаунты, созданный в /tmp настоящий WAV и реальный worker. Он проверяет

явно сообщает, что воспроизведение ещё не подключено. Backend endpoints,

Проверено в текущей среде: npm ci, typecheck/lint, runtime и Pages demo builds,
Storybook build/assemble, 15 client/session проверок, Go tests пакетов songs/auth,
оба browser integration tests и 26 story play-проверок прошли. Использован
существующий Go 1.27.3 из `/tmp/choral-toolchain`; системный Go 1.22.2 не подходит
для go.mod. Изменение версий toolchain/стека не потребовалось.

Повторная проверка замечаний #10: browser regression включает настоящий
15-секундный probe timeout (одноразовая задержка тестового ffprobe), повтор
сохранения без повторного выбора File и проверку смены ключа, а также concurrent
edit → publication conflict → explicit retry без reload с сохранением полей/файла.
Отдельный сетевой отказ загрузки проверяет сохранение ключа при повторе.
При перезагрузке тест ждёт новый документ, чтобы не читать предыдущую форму.

Регрессия потери ответа создания: Chrome обрывает ответ POST на стадии Response
после фактического commit в Go/SQLite. Тест меняет название, заметки и имя дорожки,
сохраняет ранее выбранный WAV и повторяет сохранение без reload. Проверяются
тот же ID, ровно одна песня, новые поля и ready после реального FFmpeg worker.

## Исправления редактора — Issue #31

Исходное имя читается из asset metadata API и выводится отдельно от названия
партии/статуса. Пока выбран новый File, показывается его имя и отдельно сохранённый
файл; при отказе замены сохранённое имя не меняется. Для старых ready assets без
имени — «Исходное имя недоступно». Длинные имена сокращаются в строке (полное имя
в title); пояснение сохранённого файла переносится внутри дорожки.

Прогресс загрузки, обработка и ошибки находятся в строках треков; отдельный нижний
список удалён. Save/Cancel/Listen/Publish используют общую область и стили CreateSong
в runtime и Storybook. Listen включён при хотя бы одной готовой партии; публикация
проходит прежний серверный PUT с If-Match, проверкой прав и полной готовности.
Ожидание публикации и ошибки видимы; несохранённые поля сохраняются при конфликте.
Новых зависимостей и изменений аудиодвижка нет.

### Повторное ревью #31: частичное сохранение и восстановление статуса

Подтверждённый фоновым опросом job заменяет локальную ошибку запроса статуса.
Редактор сохраняет ID принятого задания и после удаления сервером pendingJobId
при успешной обработке: готовая дорожка больше не остаётся с ошибкой сети.
Новые строки сопоставляются с серверными дорожками по позиции до получения ID
(форма допускает только добавление/сокращение списка, без перестановки). Сохранённые
ID и имена объединяются с локальными полями/File без перемонтирования формы.
После частичного успеха снятие выбора File показывает сохранённое исходное имя.

TestSongsFrontendBrowser расширен двумя регрессиями: upload принят → один getJob
оборван Chromium → фоновое подтверждение «Готово» без сохранения; два файла → первый
готов, второй отклонён реальным FFprobe → снятие первого локального выбора сохраняет
имя. Второй сценарий проверяется для новой песни и вновь добавленных строк.
API/SQLite-контракт не изменён; дизайн, авторизация и аудиодвижок не менялись.

На повторном проходе прошли npm ci, typecheck/lint, runtime/Pages demo build,
Storybook build/assemble-pages, 15 client/session тестов, Go 1.27.3 test ./...,
vet ./..., build ./..., полный TestSongsFrontendBrowser (включая 320/360/800/1280).
Отдельно в Chromium выполнены все 30 stories входа/списка/редактора с play-функциями
и проверка Pages demo. В auth-browser исправлен ожидаемый счётчик stories 26 → 30.
