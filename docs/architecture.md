# Архитектура первой рабочей версии

## Что уже согласовано

- Frontend: существующий React/TypeScript/Vite, CSS Modules, Storybook для
  состояний тех же компонентов. Этап дизайна завершён, задача — оживить UI.
- Backend: Go. Сервер проверяет все права, UI только отражает результат.
- Email + пароль, без публичной регистрации и без выбора роли на экране входа.
- Преподаватель редактирует свои песни, администратор — все и аккаунты.
- Публичные ссылки на песню/список работают без входа, только на чтение.
- Название, BPM, размер, дорожки/файлы и заметки сохраняются на сервере.
- Широкий импорт аудио через FFmpeg. Оригинал удаляется после подтверждённой
  успешной обработки; ошибки не должны приводить к потере единственной копии.

Подробные права и сессии — [authentication.md](authentication.md).
Фактическое состояние макетов — [handoff.md](handoff.md).

## Базовый план реализации

Ниже проектный baseline для первой версии, а не уже работающая инфраструктура.
Начальная задача о контрактах закрепляет конкретные схемы и параметры в
[`api/openapi.yaml`](api/openapi.yaml), [`api/README.md`](api/README.md) и
[`decisions/0001-mvp-contract.md`](decisions/0001-mvp-contract.md). До принятия
PR Issue #2 это проектный baseline, а не работающий сервис.

```text
Браузер ── HTTPS одного origin ── Go
                                 ├── /api/v1/…
                                 ├── собранный frontend
                                 ├── SQLite: метаданные, сессии, токены, задания
                                 └── постоянный каталог данных
                                      ├── временные загрузки
                                      ├── аудио для воспроизведения
                                      └── данные волн
                                          ↑
                                    FFprobe / FFmpeg worker
```

- Один Go-сервис на одном сервере. Для начала достаточно `net/http` и небольшого
  числа обоснованных библиотек, без микросервисов и отдельного брокера очередей.
- Frontend остаётся в корне; backend — в `backend/`, например `cmd/server`,
  `internal/`, `migrations/`. Не переносить существующий frontend ради структуры.
- SQLite — предложенный старт для малого числа пользователей. Драйвер, режим
  соединений/foreign keys и способ миграций выбраны в ADR; версии и реализация
  фиксируются в foundation.
- Долговечное состояние не хранится в слоях контейнера или Git. БД и файлы должны
  переживать перезапуск и обновление приложения.
- Продакшен имеет один origin: проще cookies, CSRF и загрузка аудио. В разработке
  Vite проксирует `/api`, а не требует переписывать компонентный код под другой домен.
- Storybook остаётся отдельно на Pages. GitHub Pages не исполняет Go.

## Сущности и границы ответственности

| Область | Модель/контракт |
| --- | --- |
| Пользователь | ID, нормализованный email, hash, роль, признак блокировки |
| Сессия | Серверная запись, пользователь, срок, отзыв; cookie с непрозрачным ID |
| Песня | ID, владелец, название, BPM, размер, заметки, состояние/версия |
| Дорожка | Произвольный ID, song ID, порядок, название, громкость по умолчанию, asset ID |
| Аудио | Проверенное содержимое, фактическая длительность, формат, путь по внутреннему ID |
| Задание | durable состояние обработки, попытки, результат/понятная ошибка |
| Общая ссылка | Случайный токен, область song/list, разрешённые публикации, отзыв |
| Волна | Серверные peaks и тайминг для отрисовки, а не декодирование всего файла на UI |

Точные поля и endpoints определяет Issue контракта. Песня и загрузки должны
поддерживать черновик/частичную обработку и повторный запрос без дубликатов.
Авторизация не должна доверять `owner`, `role`, file path или song ID от клиента.

Публичный список показывает только опубликованное в его области. Нужно явно
зафиксировать модель списка первой версии и различать публикацию песни и готовность
аудио. Отзыв одной ссылки не должен отзывать остальные или расширять их доступ.

## Аудио и воспроизведение

- Отдельный сценарий: загрузка → проверка FFprobe → обработка → проверка результата
  → фиксация ready/артефактов → удаление оригинала. Не выдавать ready до фиксации.
- Worker восстанавливает незавершённые задания после рестарта; лимитирует параллелизм,
  объём, время и ресурсы. Запускает программы аргументами, не shell-строкой из имени файла.
- Целевой playback-формат, параметры нормализации/ресемплинга, limits и список
  проверяемых исходных форматов выбираются в ADR. Не обещать поддержку любого файла.
- Реальный плеер использует общий аудиотайминг. Одна визуальная `setInterval`-позиция
  и независимый запуск пяти HTML audio не подтверждают синхронное воспроизведение.
- Фактические длительности, ошибки/загрузка дорожек, iOS user gesture, seek,
  пауза/возобновление и управление 1–32 дорожками входят в отдельную задачу player.
- Выбор диапазона повтора, метроном и общая сетка учитывают BPM/размер песни.

## Что должен решить первый контракт

- Схемы сущностей, API `/api/v1`, ошибки/валидация, идентичность/права и CSRF.
- Публикация song/list, готовность медиа, контракт URLs и Range-отдачи.
- Продолжительность и timing дорожек/волн, формат и limits импорта/выдачи.
- Срок сессии, bootstrap/reset аккаунтов, согласованный подсчёт 1000 символов заметки.
- Совместимое изменение песни: замена дорожек, отмена и безопасное удаление файлов.

Выбранные значения и обоснование закреплены в ADR; реализация frontend/backend
должна применять их одинаково. Не блокировать работу вопросами о каждой
библиотеке/настройке.
Реальный хостинг, домен, бюджет и секреты требуют владельца перед production-деплоем;
до этого можно подготовить и проверить локальный полный стек.

## Вне первой версии

Запись звука, автоматическое разделение голосов, соцвход, публичная регистрация,
платежи, распределённые сервисы и редизайн не входят в текущий backlog.

## Реализованный foundation

Issue #3 добавляет Go HTTP health, конфигурацию, остановку и SQLite-миграции.
Параметры и границы следующих пакетов: [backend.md](backend.md).
Остальная схема выше остаётся планом до соответствующих задач.

## Реализованная авторизация (#4)

`internal/auth` реализует IdentityProvider/Authorizer foundation: проверяет
сессию, актуальную роль, блокировку и обязательную смену пароля. `internal/users`
владеет Argon2id и транзакционным отзывом сессий. Реальные HTTP auth endpoints
и операторский CLI описаны в [backend.md](backend.md#авторизация-issue-4).
Frontend пока не подключён; songs/media используют эти интерфейсы в своих задачах.

## Реализация Issue #5

`backend/internal/songs` владеет приватными CRUD endpoints и снимками списков;
использует auth identity/authorizer и SQLite транзакции. Проверка live-сессии
повторяется внутри write-транзакции без повторного входа в односоединительный пул.
Версия защищает метаданные и live-порядок дорожек. Tracks удаляются логически,
assets retired/jobs canceled сохраняют FK и данные для уборщика #8. Новая
миграция — 0003; UI остаётся прежним. Подробности и границы — [контракт](api/README.md#реализация-songs-в-issue-5).
