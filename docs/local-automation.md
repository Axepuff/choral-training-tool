# Локальная очередь разработки через подписку ChatGPT

Компьютер выполняет **Issue → реализация → PR → отдельное ревью → исправления →
merge → следующая Issue**. Код и результаты остаются в GitHub. Терминал должен
оставаться открытым, компьютер — включённым, с интернетом и отключённым сном.
Облачный чат ChatGPT не держит эту очередь запущенной после завершения задачи.

Используется обычный **Codex CLI → Sign in with ChatGPT**. Отдельный OpenAI API-ключ
не нужен. Работа расходует лимиты Codex вашей подписки; это не безлимитный запуск.
При отказе сервиса, окончании лимита или сессии очередь останавливается. Автоматической
покупки кредитов или переключения на API в скрипте нет. Для работы строго в пределах
подписки отключите платное дополнительное использование/автопополнение Codex, если
ранее включали его в аккаунте: локальный скрипт не видит ваши платёжные настройки.

## Windows: первая установка

Установите WSL2: откройте **PowerShell от имени администратора** и выполните:

```powershell
wsl --install -d Ubuntu
```

Если Windows попросит — перезагрузите компьютер. Откройте **Ubuntu** из меню «Пуск»,
создайте Linux-пользователя и пароль. Все команды ниже выполняются в терминале
**Ubuntu**, не в PowerShell. Код лучше хранить в домашней папке Ubuntu, а не `/mnt/c`.

Установите Git, GitHub CLI, FFmpeg и Go:

```sh
sudo apt update
sudo apt install -y git gh curl ca-certificates ffmpeg golang-go
```

Установите Node.js 24 LTS через официальный установщик nvm. Скрипт скачивается
из репозитория nvm; при необходимости сначала откройте его и просмотрите:

```sh
curl -fsSL https://raw.githubusercontent.com/nvm-sh/nvm/v0.40.8/install.sh -o /tmp/install-nvm.sh
bash /tmp/install-nvm.sh
source ~/.bashrc
nvm install 24
nvm alias default 24
npm install -g @openai/codex
```

Проверьте инструменты:

```sh
node --version
git --version
gh --version
codex --version
go version
ffmpeg -version
```

Требуются Node 24+ и Codex CLI с `exec --ignore-user-config`, `--output-schema`,
`--sandbox` (совместимость флагов проверена с 0.159.2). Очередь сама проверяет эти
флаги. Настоящий Go должен ответить `go version go…`; при реализации #3 закрепляется
нужная проекту версия. Если системный Go слишком стар, обновите его по
[официальной инструкции](https://go.dev/doc/install) и проверьте `go version` снова.
Для контейнерных/E2E задач #14–15 понадобятся дополнительные инструменты, описанные
при их реализации; отсутствие инструмента останавливает задачу.

Войдите в GitHub и Codex:

```sh
gh auth login --hostname github.com --git-protocol https --web
gh auth setup-git
codex login
codex login status
```

Выберите свой аккаунт GitHub с правами записи и merge в репозиторий, а в Codex —
**Sign in with ChatGPT**, используя свою подписку. Ожидается `Logged in using ChatGPT`.
Если окно входа Codex в WSL не открылось, попробуйте `codex login --device-auth` и
откройте показанный адрес в браузере Windows. Доступность device login зависит от
настроек аккаунта. Не используйте `--with-api-key`. Не копируйте `auth.json`, OAuth
токены или пароли в GitHub Secrets, чат и файлы проекта.

Создайте **отдельный clone только для очереди**. Не запускайте в нём других агентов
и не редактируйте файлы одновременно с очередью:

```sh
mkdir -p ~/projects
cd ~/projects
gh repo clone Axepuff/choral-training-tool choral-agent-queue
cd choral-agent-queue
git config user.name "Axepuff"
git config user.email "ВАШ_ПОДТВЕРЖДЕННЫЙ_EMAIL_В_GITHUB"
npm ci
```

Вместо заглушки email укажите свой подтверждённый адрес или GitHub noreply из
**Settings → Emails**. Если первый PR очереди меняет workflows (#3), GitHub может
потребовать дополнительное разрешение `workflow`:
`gh auth refresh -h github.com -s workflow`. Разрешения выдаются обычному GitHub CLI,
а не OpenAI API. Секреты и переменные GitHub Actions для этой очереди не нужны.

## Запуск

Сначала посмотрите, что она собирается делать. Это только чтение GitHub, без
вызовов модели, push, комментариев или merge:

```sh
npm run agent:queue -- --dry-run
```

Для первого запуска выполните одну задачу полностью, включая merge при успехе:

```sh
npm run agent:queue -- --once
```

Для всей очереди:

```sh
npm run agent:queue -- --run
```

В Windows временно отключите сон в **Параметры → Система → Питание**. Не закрывайте
терминал Ubuntu. Для остановки нажмите **Ctrl+C**. После остановки или перезагрузки
откройте Ubuntu, перейдите в `~/projects/choral-agent-queue` и повторите команду.
**Save and publish** в интерфейсе облачной среды для этого не используется.

## Порядок и правила

- Очередь последовательно выполняет #2–12, #14, #15 с учётом всех зависимостей,
  включая зависимости «для завершения». Epic #1, NEXT #13 и production #16 исключены.
  Серверы, платные ресурсы и production-секреты автоматически не создаются.
- Зависимость принята, только если Issue закрыта как completed и найден merged PR
  с `Closes #N`/`Fixes #N` в `main`. Простого закрытия Issue недостаточно.
- Открытый PR этой Issue подхватывается для ревью. Fork, draft, несколько PR на
  одну Issue, конфликт и чужие незакоммиченные изменения требуют ручного разбора.
- Реализация и каждое ревью — новые процессы `codex exec`, без переноса истории
  исполнителя в ревью. Исполнитель использует `workspace-write`, reviewer —
  `read-only`; повышение прав и полный доступ не включаются. Личные настройки
  моделей игнорируются, provider закреплён на OpenAI и ChatGPT login. Storybook MCP
  в очереди отключён, поэтому работающий Storybook не требуется.
- Контроллер делает commit/push/PR, а модель получает задание только на код или ревью.
  Credentials из окружения не передаются модели и процессам проверок. Это автоматизация
  для собственного доверенного репозитория, не изоляция враждебного кода от аккаунта:
  процессы работают от вашего Linux-пользователя. Используйте отдельный clone без
  production-секретов. Пользовательский ввод Issue не исполняется как shell-код.
- Обязательны `npm ci`, typecheck, lint, build, build-storybook, сборка Pages и тесты
  очереди. Если появились scripts `test`, `test:api`, `test:e2e`, они тоже запускаются.
  При наличии `backend/go.mod` добавляются настоящий `go version`, `go test ./...`,
  `go vet ./...`, `go build ./...`. Дополнительные acceptance-проверки оценивает reviewer;
  одна сборка Storybook не считается запуском stories/play.
- Ревью привязано к SHA `HEAD` и `main`. Нужны выполненные acceptance criteria и
  пустой список замечаний, включая P2. Ошибка тестов или замечания запускают
  исправление и все проверки заново. Максимум **три попытки исправлений на задачу**,
  счётчик сохраняется между запусками. Ошибка модели/квота/невалидное ревью останавливает
  очередь. На вызов Codex отведено 90 минут, на одну проверку — 20 минут.
- Дополнительные GitHub checks ожидаются до 20 минут. Если checks нет, это явно
  отмечается; основание merge — локальные проверки и независимое ревью. Человеческое
  `changes requested`, незакрытые review threads и branch protection не обходятся.
  Для повторного запуска после человеческого отклонения reviewer должен одобрить PR.
- Перед merge повторно проверяются SHA; команда merge использует `--match-head-commit`,
  без `--admin`. Если `main` изменился — нужен новый проход. GitHub не предоставляет
  этой команде атомарной проверки SHA базы; для строгой защиты при одновременных
  merge включите в branch protection требование актуальности ветки. Не объединяйте
  другие PR параллельно с работающей очередью без необходимости.
- Очередь не может менять `AGENTS.md`, `.codex/`, `.agents/` и свой контроллер
  `scripts/agent-queue/`. Такие изменения выполняются отдельным ручным PR. Обычный
  CI workflow для #3 разрешён. Независимое ревью моделью не гарантирует отсутствия
  ошибок; проверяйте итоговую работу перед запуском настоящего сервера.

## Если остановилась

```sh
npm run agent:queue -- --status
```

В выводе — Issue, ветка, PR и использованные попытки исправлений. Логи и состояние
находятся в `.git/choral-queue/`, не попадают в Git. По пути из терминала можно
посмотреть причину остановки. Логи содержат код и результаты команд; не публикуйте
их целиком без просмотра. Токены авторизации намеренно не запрашиваются и не выводятся.

При исчерпании лимита дождитесь его восстановления и повторите `--once`/`--run`.
При завершившейся сессии сначала выполните `codex login`. После Ctrl+C очередь
не откатывает изменения: если рабочее дерево изменено, сначала просмотрите его и
вручную сохраните нужные изменения коммитом в показанной ветке; затем повторите
запуск. Конфликт merge разрешите и закоммитьте вручную. После трёх неудачных
исправлений разберите PR и исправьте его вручную: повторный запуск сможет проверить
и объединить готовое исправление, но четвёртый автоматический fix не запустится.

Если компьютер аварийно выключился, может остаться lock. После проверки, что
очередь действительно остановлена, выполните:

```sh
npm run agent:queue -- --unlock
```

Живой процесс не позволяет снять свой lock. Не удаляйте lock или state во время
работы. Не переключайте ветки в этом clone вручную без остановки очереди.

Если в логе Codex есть `invalid transport` в `mcp_servers.choral_storybook`,
обновите очередь до исправления из `main`: CLI требует URL даже у отключённого MCP.
При остановленной очереди и чистом рабочем дереве выполните **в текущей ветке
задачи**, сохраняя `.git/choral-queue/state.json`:

```sh
git status --short
git fetch origin +refs/heads/main:refs/remotes/origin/main
git merge --no-edit origin/main
npm run test:agent-cli
npm run agent:queue -- --once
```

Продолжайте после `git status --short`, только если вывод пустой. Если есть правки —
сначала просмотрите и сохраните их коммитом. Переключение на `main` и удаление state
для этого обновления не требуются. Storybook для очереди запускать не нужно.

## Проверка самой автоматизации

```sh
npm run test:agent-queue
npm run test:agent-cli
npm run agent:queue -- --dry-run
```

Поведенческие тесты используют заглушки модели/GitHub и временные Git-репозитории.
Они не вызывают платный API или Codex inference, не создают PR и не объединяют
настоящие задачи. Dry-run проверяет чтение реального backlog. Первый реальный
вызов Codex нужно проверить на вашем компьютере после входа; облачные тесты
не подтверждают вход в ваш локальный аккаунт.

`test:agent-cli` отдельно требует установленный Codex CLI. Он проверяет реальные
аргументы реализации и ревью на пустой временной конфигурации с заведомо неизвестным
provider. Ожидаемый отказ происходит до авторизации и inference; модель не вызывается.
Контрольный сценарий воспроизводит исходный `invalid transport` без URL. Проверено
на Codex CLI 0.159.2 и 0.163.0; эта проверка не подтверждает доступность самой модели.
