# Замечания владельца при проверке PR #30

Проверка на отдельном стенде с Go backend и HTTPS-доступом. Подтверждённое
устройство владельца — iPhone 16, iOS 26.6.2, Safari. Полный мобильный smoke
не пройден: после исправления чтения timestamps обнаружен следующий блокер
декодирования звука на устройстве (пункт 4).

## 1. Отдельный нижний блок редактора непонятен

Под формой отдельным списком показаны состояния дорожек, стандартные браузерные
кнопки «Слушать песню», «Опубликовать сохранённую песню» и статус публикации.
Блок выбивается из согласованного компактного интерфейса.

Согласованное направление: состояния загрузки/обработки возле соответствующих
файлов; прослушивание и публикация в общей области действий формы; запуск
прослушивания при наличии готового аудио. Функцию публикации сохранить.

Статус: зафиксировано, исправление UI ещё не выполнено.

## 2. После загрузки потеряны названия файлов

Вместо исходных имён у двух партий показана общая надпись «Готовая дорожка».
`songForm()` подставляет эту строку, исходное имя отсутствует в текущем Song API.

Нужно сохранять имя как метаданные после обработки/удаления оригинала и возвращать
при повторном открытии песни; показывать его отдельно от статуса. Учесть замену
файла и длинные имена без переполнения мобильной страницы. Имя не должно становиться
путём файлового хранилища.

Статус: зафиксировано, изменение хранения/API/UI ещё не выполнено.

## 3. Обычные WAV не воспроизводятся — блокер

Обе дорожки показывают «Неподдерживаемый AAC timing», волны отсутствуют, транспорт
остаётся на 0:00. Воспроизведено локально: серверный filter `asetpts=N/SR/TB`
при конвертации WAV 44,1 kHz в mono AAC 48 kHz даёт округлённые `stts` 1023/1025.
Плеер ошибочно требовал строго 1024 для каждого непоследнего frame.

Reader исправлен: учитывает ограниченное округление без накопления дрейфа,
проверяет целостность/счётчики таблицы. Добавлены реальные WAV regressions
8–96 kHz, malformed/drift cases и браузерные fixtures с серверным filter.
Результаты: [audio-player.md](../audio-player.md#исправление-aac-timing-после-ручной-проверки--22-октября-2026).

Статус: локальные регрессии прошли; после обновления владелец видит волны и
«Готово» на iPhone, но при Play возникает следующий блокер (пункт 4).
Замечания 1–2 этим исправлением не закрыты.

## 4. Safari/iPhone: при первом Play — «Неподдерживаемый декодер AAC»

Устройство: iPhone 16, iOS 26.6.2, Safari. Индексы/peaks загружены и дорожки
помечены «Готово», но первое декодирование исключает обе дорожки и транспорт
показывает «Нет доступных дорожек». Это не успешная проверка Safari.

Сообщение reader объединяло несовпадение sample rate и недостаточное число
PCM samples после decode. В dev-версии добавлены разные коды и раскрываемая
«Диагностика воспроизведения»: context/decoded rate, encoded/decoded samples,
offset, требуемая длина и диапазон окна. Она не содержит URL, cookies или
содержимого аудио; production UI её не отображает.

Получена диагностика обеих дорожек: `AAC_SHORT_PCM`, context/decoded rate 48000,
encoded 194560, decoded 192448, offset 1024, required 192000, окно 0–4 секунды.
Декодер возвращает на 2112 samples меньше числа samples в AAC-пакетах; несовпадение
sample rate исключено. Такой результат согласуется с неявным AAC priming при
отсутствии edit list в собранном плеером коротком MP4.

Reader теперь задаёт явный нулевой edit для каждого окна, точные длительности
в sample timebase и удаляет оставшиеся от полной записи sample groups/trim metadata.
Исходный priming файла применяется при извлечении PCM один раз. Укороченный PCM
по-прежнему отклоняется, тишина не добавляется. Повторная загрузка файлов не нужна.

Повторная проверка владельца после обновления: снова `AAC_SHORT_PCM` с теми же
числами. Правка metadata **не решила проблему** на устройстве; unit-модель
неявного среза не соответствовала этому поведению Safari.

Следующее исправление: при подтверждённой поддержке AAC WebCodecs reader
декодирует исходные пакеты в module Worker без `decodeAudioData` и MP4 edit semantics. Backend,
существующие media/peaks и файлы не меняются. Dev-отчёт получил `readerVersion: 2`,
`decoder` и причину ошибки пакетного декодера. Старый путь остаётся только для
браузеров без поддержанного AudioDecoder; при коротком PCM он по-прежнему
показывает ошибку. Общее сообщение теперь «Не удалось декодировать аудиофрагмент»,
чтобы не объявлять отсутствие поддержки AAC. См. [описание пути и проверок](../audio-player.md#пакетное-декодирование-после-повторного-отказа-safari).

Статус: прошли 39 аудиотестов, lint/typecheck, обе сборки/assemble-pages и браузерный
прогон Chromium с 60 секундами непрерывного транспорта 32 дорожек, перемотками,
сравнением PCM и принудительно выключенным старым decode path. Новый путь
на физическом iPhone после этой смены декодера ещё не проверен; mobile smoke
остаётся открытым.
