## Конфигурация для согласования

`Internet → existing Caddy → 127.0.0.1:8080 → choral Compose → private data volume`.

Используем существующие Dockerfile, Compose, backup/restore и systemd timer PR #43.
[`deploy/choral.caddy`](../deploy/choral.caddy) добавляет только `choral-train.ru`.
Caddy получает/обновляет сертификат автоматически. Не нужен отдельный Certbot.
Лимит тела — 105906176 bytes (101 MiB с multipart overhead; файл до 100 MiB).
Idle read/write — 30/35 секунд; upstream dial — 5 секунд, response headers и
read/write — 35 секунд. Общий backend read/write budget остаётся 30 секунд;
медленная загрузка может его исчерпать. Host, URI, Range/HEAD сохраняются,
X-Forwarded-Proto задаётся Caddy. Кеширование приватных ответов не включается.

Access logging намеренно не включается даже с `output discard`: именованный
logger может включить fallback access log для соседних сайтов на общем listener.
`handle_errors` возвращает фиксированный текст и исходный код ошибки proxy,
не подставляя URI/ошибку в тело. Ответы API, включая JSON ошибок, проходят без
замены. Это проверено при INFO logging; **debug/trace включать нельзя**.
Проверка кандидата отказывается работать при существующих custom/access/trace
logs. Добавление логирования, CDN/WAF или обновление Caddy требует повторной
проверки токенов в пути/query, Referer, Cookie и Authorization.

Документация Caddy: [reverse_proxy](https://caddyserver.com/docs/caddyfile/directives/reverse_proxy),
[request_body](https://caddyserver.com/docs/caddyfile/directives/request_body),
[timeouts](https://caddyserver.com/docs/caddyfile/directives/timeouts),
[handle_errors](https://caddyserver.com/docs/caddyfile/directives/handle_errors).
Директива timeouts экспериментальная; проверяем именно установленную 2.11.7.

## Проверка без установки

```sh
python3 scripts/check-caddy.py
# Новый приватный файл, никогда не выводить его целиком в чат/CI:
python3 scripts/prepare-caddy.py /etc/caddy/Caddyfile /tmp/choral-Caddyfile.candidate
```

Первый скрипт запускает отдельный непривилегированный Caddy на loopback high ports,
временный доверенный только тестом TLS-сертификат и синтетический upstream. Не
обращается к ACME, системному trust store или admin API действующего Caddy.
Проверяет TLS, 200/404/502/413/400, реальную передачу 101 MiB + 1 byte, небольшой
upload, HEAD/Range, HTTP redirect, соседний сайт и его ошибку, отсутствие секретов
в stdout/stderr. Это proxy integration, не full-stack production smoke.

Второй скрипт читает текущий Caddyfile, добавляет fragment и проверяет JSON после
адаптации: прежние настройки/маршруты не должны измениться. Игнорируется только
перенумерация внутренних групп маршрутов с сохранением их связей. Кандидат
создаётся с mode 0600, существующий файл/символическая ссылка не перезаписывается.
Конфигурация не печатается, сервис не перезагружается. Относительные imports
разрешаются от каталога исходного Caddyfile; устанавливать кандидат нужно туда же.
Не использовать старый кандидат после чужих изменений: сформировать заново.

## Порядок после разрешения установки

1. Подтвердить DHCP reservation для `.101`, свежие bytes/inodes/RAM, отсутствие
   конфликтующего Compose project/volume `choral`, успешные checks выбранного SHA.
   Лимит приложения 3 GiB — потолок, не резерв памяти. На общем ноутбуке нельзя
   считать 3,7 GiB MemAvailable достаточной гарантией. Пока Immich выполняет тяжёлую
   работу, не запускать сборку и worker одновременно. Выбрать спокойное окно или
   собрать тот же immutable image на другой amd64-машине и перенести его.
   Не останавливать соседние приложения, не менять их лимиты и не добавлять swap
   без согласования. После smoke измерить реальную пиковую RAM/CPU двух обработок.
2. Подготовить root-owned `/opt/choral` из одобренного SHA и `.env` mode 0600:
   `CHORAL_ORIGIN=https://choral-train.ru`, `CHORAL_IMAGE_TAG=<полный SHA>`,
   `COMPOSE_PROJECT_NAME=choral`. Сохранить image ID. Данные оставить в отдельном
   Compose volume; не менять Docker data-root. Собрать/перенести image и выполнить
   container smoke в изолированном project до production. Сборка тоже требует RAM
   и места, не выполнять её автоматически в текущей диагностической сессии.
3. Приватно сохранить текущий Caddyfile с metadata/permissions. Сформировать свежий
   кандидат через `prepare-caddy.py`; сверить оригинал непосредственно перед
   установкой, чтобы не затереть чужие изменения. Запустить приложение по общему
   runbook, проверить loopback `/readyz`. Если не ready — не переключать proxy.
4. После согласования установить кандидат рядом с оригиналом, сохранив owner/mode
   и разрешение чтения сервисом Caddy. Выполнить `caddy validate` в контексте
   сервисного пользователя и правильного каталога imports. Проверить код возврата,
   затем атомарно заменить Caddyfile и выполнить `systemctl reload caddy`.
   Не использовать restart/stop и не изменять firewall/NAT/SSH/Tailscale.
   Не оставлять публичный диагностический endpoint вместо настоящего backend.
5. Проверить все четыре прежних сайта до/после, новый HTTP redirect, ACME,
   `https://choral-train.ru/readyz` без `-k`, frontend/deep links/API и закрытый
   извне 8080. Проверку нового HTTPS повторить через мобильный интернет. При
   проблеме восстановить сохранённый Caddyfile, validate и reload; данные/volume
   не удалять. Первый rollout не требует миграции данных соседних приложений.
6. Только после отдельного согласования создать начальные аккаунты через stdin,
   выполнить смену временных паролей и полный пользовательский smoke по
   [deployment.md](deployment.md#приёмка-на-настоящем-origin). Email/пароли не
   помещать в PR. Затем backup → clean restore в отдельном volume, контрольная
   песня/media/ключ ссылки, проверка внешней копии и уведомления. Timer включить
   только после этих проверок и согласования времени/retention.

Для backup пока предложен существующий `/var/backups/choral` (тот же системный
диск). Это лишь локальная копия; внешний зашифрованный backup и канал оповещения
нужно выбрать с владельцем. Наличие диска `/mnt/storage` само по себе не доказывает
независимость/надёжность внешней копии. Автоудаление копий не включать.

## Результат подготовки

На Caddy 2.11.7 прошёл изолированный proxy integration выше. Кандидат на основе
реального `/etc/caddy/Caddyfile` прошёл структурную проверку сохранности всех
существующих настроек/маршрутов; полный приватный конфиг не добавлен в Git.
CI использует официальный Caddy 2.11.7 amd64 archive с закреплённым SHA-256.
Это не установка, не ACME и не приёмка приложения на публичном origin.
Предыдущие full-stack/container результаты находятся в deployment.md/e2e.md;
повтор на этом ноутбуке и production backup/restore пока не выполнены.
