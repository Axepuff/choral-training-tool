# Как продолжать работу с другими агентами

## Новый чат

Выберите тот же репозиторий `Axepuff/choral-training-tool` и актуальный `main`.
Историю этого чата переносить не требуется. Пример первого сообщения:

> Работай в Axepuff/choral-training-tool. Выполни Issue #N.
> Прочитай AGENTS.md и связанные документы. Проверь, что зависимости Issue закрыты
> или их контракты уже объединены. Создай отдельную ветку и PR с проверками.
> Согласованный дизайн сохраняй. Другие Issues попутно не реализуй.

Замените `#N` номером из [roadmap](roadmap.md). Все существенные результаты
должны остаться в GitHub, а не только в ответе агента.

## Параллельная работа

- Сначала задача API/данных. После неё — каркас Go и первая задача frontend-клиента
  на контрактных моках. Агентам нельзя независимо придумывать разные API.
- По готовому каркасу backend auth и songs могут идти параллельно в своих пакетах,
  используя заранее согласованный интерфейс identity/authorizer.
- Аудиоengine можно разрабатывать на fixtures параллельно с серверной обработкой;
  рабочая интеграция всё равно требует готовых media API.
- Если задачи меняют один файл, например `src/main.tsx` или плеер, выполняйте их
  по очереди либо заранее закрепляйте, какой PR объединяет изменения.
- Одна миграционная последовательность/общий API contract имеют одного владельца
  интеграции. Зависимый агент обновляет ветку после объединения prerequisite PR.
- Для нескольких самостоятельных агентов запускайте отдельные облачные задачи
  с отдельными ветками. Один checkout не подходит для одновременного переключения
  Git-веток несколькими агентами. Worktree для этого проекта автоматически не создавать.

## Субагенты внутри одной задачи

Пример поручения:

> Выполни Issue #N. Подключи субагента для независимой проверки прав доступа,
> другому поручить проверку тестовых сценариев. Основной агент интегрирует результат,
> запускает проверки и создаёт один PR.

Для небольших изменений достаточно одного агента. Субагенты полезны для независимой
проверки и отдельных модулей, а не как постоянное хранилище контекста.

## Когда задача готова

1. Выполнены acceptance criteria; проходят относящиеся к изменению проверки.
2. PR содержит `Closes #N`, понятное описание, результаты и ограничения.
3. Контракты/документация обновлены вместе с изменениями.
4. Человек просматривает PR и объединяет его с `main`; зависимые агенты начинают
   интеграцию с этого коммита. До production нужен проход интеграционных проверок.

По поручению владельца этот цикл можно выполнять локальной очередью:
**Issue → реализация → PR → отдельное ревью → исправления → проверки → merge →
следующая Issue**. Она работает на компьютере владельца через Codex CLI с входом
ChatGPT, без OpenAI API-ключа. Установка на Windows через WSL2 и правила остановки
описаны в [local-automation.md](local-automation.md). Для обычных облачных агентов
сохраняется завершение через PR; автоматически объединяет только контроллер очереди.

В `main` уже настроена автоматическая публикация статического preview. Поэтому
для следующих задач используем PR, а не серию прямых push в основную ветку.

## Что хранит GitHub и что делает Codex

- Код, документация, ветки, Issues и PR хранятся в GitHub.
- Облачная задача Codex получает checkout и выполняет команды. Процессы и память
  чата не заменяют сервер приложения и постоянное файловое хранилище.
- **Save and publish** в настройках среды публикует её конфигурацию; его не нужно
  нажимать для каждого чата/PR. При добавлении Go/FFmpeg задача foundation должна
  сохранить нужные setup-инструкции и проверить настоящий toolchain.
- Текущий Pages содержит только frontend/Storybook. Backend первой версии
  будет работать на отдельном сервере; secrets вводятся в настройки, не в чат/Git.
