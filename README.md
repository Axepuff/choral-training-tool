# Хор · Репетиция

Мобильное веб-приложение на React 19, строгом TypeScript и Vite 8. Обычный CSS
и CSS Modules, без UI-кита. React выбран вместо Preact с разрешения пользователя:
нативный Preact framework Storybook пока не генерирует манифест API для MCP.

## Управление сервером вручную

Агенты для эксплуатации не нужны. Команды ниже рассчитаны на **существующий**
Debian-ноутбук `velette`: Docker, Compose и Caddy уже установлены. Не повторяйте
первичную установку поверх него. С компьютера с вашим Tailscale подключитесь:

```sh
ssh axepuff@velette
```

На самом ноутбуке достаточно открыть терминал. Рабочая копия сервера —
`/opt/choral`, данные — Docker volume `choral_data`, настройки — закрытый
`/opt/choral/.env`. Caddy принимает HTTPS и передаёт запросы на `127.0.0.1:8080`.
Исходники разработчика в `~/projects/choral-training-tool` — другая копия.

### Проверить состояние

```sh
cd /opt/choral
sudo docker compose ps
curl --fail https://choral-train.ru/readyz
sudo docker compose logs --tail 50 app
sudo systemctl is-active caddy tailscaled ssh
df -h / /var/backups
df -i /
```

Нормальное состояние приложения — `healthy`, readiness возвращает HTTP 200.
Затем откройте сайт, войдите и воспроизведите песню: readiness не проверяет звук.
Не публикуйте содержимое `.env`, резервных копий, cookies или паролей.
Используйте именно **https://choral-train.ru**: HTTP на порту 80 пока может
перенаправлять на страницу Keenetic. Обновление приложения этого не исправляет.

### Обновить приложение

Сначала объедините проверенный PR через GitHub и дождитесь зелёных проверок.
Выберите **полный SHA коммита** — 40 символов из GitHub. Сам merge ничего на
сервере не устанавливает. PR #43 объединён: выбирайте проверенный коммит из `main`.
Не деплойте произвольную вершину ветки без проверки её изменений.

Предупредите преподавателя о коротком перерыве: во время резервного копирования
и перезапуска сайт несколько секунд/минут может отвечать ошибкой. Сборка до этого
идёт при работающем приложении и на ноутбуке может занять несколько минут.

Откройте отдельную root-сессию; выполняйте следующие блоки в ней по порядку.
`set -e` остановит процедуру при ошибке. Не продолжайте после ошибки вслепую.

```sh
sudo -i
set -eu
cd /opt/choral
exec 9>/run/lock/choral-maintenance.lock
flock -n 9
# Если lock занят — другой оператор/backup работает; повторите позже.
test -z "$(git status --porcelain)"
git fetch origin
read -r -p 'Полный SHA проверенного релиза: ' RELEASE
[[ "$RELEASE" =~ ^[0-9a-f]{40}$ ]]
git cat-file -e "$RELEASE^{commit}"
OLD_RELEASE=$(git rev-parse HEAD)
OLD_IMAGE=$(docker inspect --format '{{.Config.Image}}' choral-app-1)
```

Создайте отдельный каталог исходников и соберите образ с уникальным тегом. Уже
настроенный builder `choral-issue16` ограничен 2 CPU/2 GiB RAM и сам запустится.

```sh
BUILD_DIR=$(mktemp -d /tmp/choral-release.XXXXXX)
git archive "$RELEASE" | tar -x -C "$BUILD_DIR"
docker buildx build --builder choral-issue16 --load -t "choral:$RELEASE" "$BUILD_DIR"
docker buildx stop choral-issue16
rm -rf -- "$BUILD_DIR"
```

Перед переключением остановите запись и сохраните **весь** volume. Секреты и
пароли входят в копию: доступ к каталогу только у root. Не запускайте команды
управления аккаунтами в другой сессии во время backup.

```sh
install -d -m 700 /var/backups/choral
BACKUP="/var/backups/choral/$(date -u +%Y%m%dT%H%M%SZ)-before-update"
# При ошибке до переключения вернуть прежнее приложение.
trap 'docker compose up -d --no-build --wait --wait-timeout 90 app' EXIT
docker compose stop app
test "$(docker inspect -f '{{.State.ExitCode}}' choral-app-1)" = 0
sh scripts/backup-restore.sh backup "$BACKUP"
cp -p .env "$BACKUP/env.before"
printf '%s\n' "$OLD_RELEASE" > "$BACKUP/COMMIT"
printf '%s\n' "$OLD_IMAGE" > "$BACKUP/IMAGE_TAG"
docker inspect -f '{{.Image}}' choral-app-1 > "$BACKUP/IMAGE_ID"
# Копия завершена. Дальнейшая ошибка требует ручного разбора/отката ниже.
trap - EXIT
git switch --detach "$RELEASE"
# В существующей .env меняется только тег образа.
test "$(grep -c '^CHORAL_IMAGE_TAG=' .env)" = 1
sed -i "s/^CHORAL_IMAGE_TAG=.*/CHORAL_IMAGE_TAG=$RELEASE/" .env
chmod 600 .env
docker compose up -d --no-build --wait --wait-timeout 90 app
curl --fail http://127.0.0.1:8080/readyz
curl --fail https://choral-train.ru/readyz
docker compose ps
exit
```

Проверьте вход, список и звук в браузере. Не удаляйте предыдущий образ и backup.
Нельзя выполнять `docker compose down -v`: это удалит песни и аккаунты.
Caddy, DNS, роутер, SSH и Tailscale при обычном обновлении менять не требуется.

### Если обновление не работает

Сначала посмотрите `sudo docker compose logs --tail 100 app`. Если релиз **не
меняет схему БД** и совместимость подтверждена (как исправление лимита #47),
можно вернуть предыдущий код и `.env`, сохранив текущие песни и пароли:

```sh
sudo -i
set -eu
cd /opt/choral
exec 9>/run/lock/choral-maintenance.lock
flock -n 9
read -r -p 'Полный путь к backup перед обновлением: ' BACKUP
OLD_RELEASE=$(cat "$BACKUP/COMMIT")
docker compose stop app
git switch --detach "$OLD_RELEASE"
cp -p "$BACKUP/env.before" .env
docker compose up -d --no-build --wait --wait-timeout 90 app
curl --fail https://choral-train.ru/readyz
exit
```

После миграций БД одного старого образа недостаточно. Восстанавливайте старый
образ и полный backup **в новый пустой volume** по
[инструкции восстановления](docs/operations.md#восстановление-в-чистый-volume).
Не распаковывайте архив поверх рабочего volume. Возврат данных из копии теряет
изменения после её создания; сначала выберите нужную копию и согласуйте это.

### Сделать резервную копию отдельно

После согласования короткого перерыва запустите установленный service вручную.
Он останавливает приложение и запускает его обратно даже при ошибке копирования,
затем сохраняет вторую копию на HDD. Каталог назначения должен существовать.

```sh
sudo install -d -m 700 /var/backups/choral
sudo systemctl start choral-backup.service
sudo systemctl show choral-backup.service -p Result -p ExecMainStatus
```

Service сам берёт maintenance lock и читает настройки второй копии. Не оборачивайте
`systemctl start` в дополнительный flock: это помешает service получить lock.
Запускайте штатный ручной backup через service, чтобы Beszel получил результат
именно этой попытки; прямой вызов скрипта не обновляет systemd Result.

Копии содержат чувствительные данные. Копия на том же диске не защищает от его
поломки; нужна отдельная защищённая копия на другом носителе и проверка восстановления.
Автоматическое расписание backup **включено**. Первый запуск назначен на
30 октября 2026 в 06:00 МСК; его успешный результат ещё нужно проверить. Согласованы ежедневные
06:00 по Москве (03:00 UTC), перерыв до двух минут и хранение месяц.
Копия на отдельном HDD `/mnt/storage/choral-backups` защищена правами root-only,
без шифрования по выбору владельца. Для уведомлений выбран существующий Beszel
с почтой; его проверки choral/backup настроены, получение тестовой тревоги
подтверждено владельцем. После отдельного согласия включена очистка только
ежедневных пар старше 31 суток; ручные/pre-update копии сохраняются.
Проверка копии от 29 октября: SQLite, файлы, ключи и чтение аудио восстановлены
в изолированном volume; исходная гостевая ссылка ещё не проверена.
[Результаты и оставшиеся решения](docs/deployment-velette.md#эксплуатационная-проверка--29-октября-2026).
Гостевые song/list ссылки, отзыв и серверный запрет изменений проверены на
отдельной технической песне. Она оставлена до ночной проверки восстановления;
пользовательские песни не менялись. Автоматический restore на 06:10 и очистка
ежедневных копий старше 31 суток включены по отдельному разрешению владельца.
Первый restore назначен на 30 октября 2026 в 06:10 МСК; результата ещё нет.

### Пароли и аккаунты

Обычная смена пароля выполняется самим пользователем на сайте. Если преподаватель
забыл пароль, администратор может сбросить его через API управления аккаунтами;
готового интерфейса управления пользователями пока нет. CLI `reset-admin`
восстанавливает только администратора — для преподавателя его не используйте.
Контракт сброса: `PUT /api/v1/admin/users/{userId}/password`, сессия администратора
и CSRF; подробности в [API](docs/api/README.md#сессии-csrf-и-аккаунты).

Для создания нового преподавателя в Bash на сервере (пароль не попадёт в историю
и не будет показан при вводе; минимум 12 символов):

```sh
cd /opt/choral
sudo -v
read -r -p 'Email нового преподавателя: ' TEACHER_EMAIL
read -r -s -p 'Временный пароль: ' CHORAL_PASSWORD
printf '\n'
printf '%s' "$CHORAL_PASSWORD" | sudo flock -n /run/lock/choral-maintenance.lock docker compose exec -T app choral-accounts create-teacher "$TEACHER_EMAIL"
unset CHORAL_PASSWORD
```

Для восстановления администратора используйте такой же скрытый ввод, но команду
`choral-accounts reset-admin` без email. `bootstrap EMAIL` нужен только для самого
первого администратора на новой установке; существующие аккаунты повторно не создавайте.
Передайте временный пароль человеку лично; после обязательной смены удалите его
временный файл, если создавали. Пароль не истекает по таймеру, но после смены старый
больше не подходит. Теперь 20 ошибок за 5 минут дают паузу 30 секунд; общий лимит
сервера 20 проверок в минуту может потребовать подождать до минуты.

Подробности сервера: [velette](docs/deployment-velette.md),
[deployment](docs/deployment.md), [эксплуатация](docs/operations.md).

## Что реализовано

- Общие компоненты и стили для приложения и Storybook.
- Токены цветов, типографики, отступов и скруглений: `src/styles/tokens.css`.
- Светлый интерфейс от 360 px, области касания минимум 44 × 44 px.
- TrackControls: громкость, взаимоисключающие Solo/Mute, состояние загрузки.
  Включение Mute отключает Solo и наоборот; можно выбрать несколько Solo-партий.
- Плеер: четыре голоса и минус, цветные волны на одном таймлайне с сеткой тактов 4/4, курсор,
  верхний play/pause, перемотка, возврат к началу, выбор первого/последнего такта повтора и метроном.
  Компактный микшер: пять партий в ряд, кнопки S/M и вертикальные фейдеры.
- Stories компонентов и страниц; интерактивные состояния содержат `play`-проверки.
- Отдельная story «16 тактов · горизонтальная прокрутка»: волны и сетка прокручиваются вместе, курсор остаётся видимым при воспроизведении.
- Story «Мобильный · горизонтально · 16 тактов»: при повороте телефона таймлайн занимает всю ширину, S/M размещаются рядом с вертикальными фейдерами.
- Viewport-пресеты: 360, 390, 768 и 1280 px.

Описание пяти партий выше относится к демонстрации. Runtime использует настоящие
media/peaks из Go API и Web Audio, с выбором тактов и звуковым метрономом;
Stories/Pages demo остаются явно визуальными, без звука. Реальная авторизация,
сохранение и загрузка файлов уже подключены; актуальное состояние см. в
[docs/handoff.md](docs/handoff.md). Правила повтора, timing и ограничения устройств:
[docs/audio-player.md](docs/audio-player.md#выбор-тактов-и-метроном--issue-12).

## Официальный Storybook MCP и Codex

Storybook и официальный `@storybook/addon-mcp` закреплены на стабильной версии
10.6.2. Предварительные npm-релизы не нужны, однако AI API Storybook официально
имеет статус **preview** и может изменяться.

В `.storybook/main.ts` включены addon и `componentsManifest`.
При запущенном `npm run storybook` сервер MCP доступен по адресу
`http://127.0.0.1:6006/mcp` через Streamable HTTP. Статическая сборка его не запускает.

Проектная конфигурация Codex находится в `.codex/config.toml`; Codex читает её
в доверенном проекте. Альтернативная регистрация через CLI:

```sh
codex mcp add choral_storybook --url http://127.0.0.1:6006/mcp
codex mcp get choral_storybook --json
```

После регистрации запустите новую сессию Codex из папки проекта, оставив
Storybook работающим. Попросите агента вызвать `docs-list`, затем `docs-show`
с `id: "components-track-controls"`. Codex CLI 0.159.2 поддерживает этот транспорт.
Сам запуск Storybook или наличие конфигурации не доказывают подключение агента.

Проверка реального MCP-протокола без дополнительных зависимостей:

```sh
npm run check:mcp
```

Скрипт выполняет `initialize`, `tools/list`, `docs-list`, `docs-show`, проверяет
наличие обоих компонентов и свойств TrackControls. При ошибке завершается
с ненулевым кодом. Эти запросы проверены из облачного агента. Динамическое появление
MCP-инструментов в текущем облачном чате не подтверждено; локальная конфигурация
CLI не гарантирует её поддержку облачным клиентом. Новую локальную сессию нужно
проверить приведёнными выше вызовами.

Инструменты MCP для тестирования требуют отдельного Vitest-addon; он не установлен.
Для этой задачи используются инструменты документации и браузерные `play`-проверки.

Документация: [Storybook MCP](https://storybook.js.org/docs/ai/mcp/overview),
[поддержка framework](https://github.com/storybookjs/storybook/blob/v10.6.2/docs/ai/mcp/overview.mdx#framework-support),
[Codex MCP](https://developers.openai.com/codex/mcp/).

В облачной песочнице при недоступном домашнем npm-кеше можно использовать:
`npm ci --cache /tmp/choral-npm-cache --no-audit --no-fund`.

### Создание песни (макет)

В приложении откройте `/?page=create-song`; в Storybook — «Страницы → Создание песни».
Форма: название, BPM (20–300), размер (1–32 доли; длительность 1/1–1/32),
1–32 трека с названиями и локальным выбором файлов, заметки до 1000 символов.
Пять stories показывают пустую/заполненную форму, мобильный вариант, выбранные
файлы и отсутствие файлов. Кнопка создания проверяет форму, но ничего не сохраняет.

Файловый диалог намеренно не ограничен MIME/расширением: браузерная поддержка
декодирования не должна ограничивать будущий серверный импорт. FFmpeg на Go backend
пока не подключён. План: проверять реальное содержимое и доступный декодер на сервере,
конвертировать в целевой формат, проверить результат и сохранить его; только затем
удалять оригинал. Набор поддерживаемых форматов зависит от сборки FFmpeg; размеры,
длительности, целевой формат и обработку ошибок нужно определить при реализации backend.
Сейчас файлы хранятся только в памяти страницы, при её закрытии выбор теряется.

### Вход (макет)

`/?page=sign-in`, Storybook — «Страницы → Вход». Email, пароль, показ/скрытие пароля,
состояния проверки, неверных данных и ошибки соединения. Передачи данных и реального
входа пока нет. Согласованные роли, публичные ссылки и план серверной сессии описаны
в [docs/authentication.md](docs/authentication.md).

### Список песен (макет)

`/?page=library`, Storybook — «Страницы → Список песен». Поиск по названию, сортировка,
создание песни, переход в демонстрационный плеер и копирование демо-ссылки.
Заголовок списка — «Песни». Гость видит опубликованные записи только для просмотра;
преподаватель — свои и опубликованные, редактирует свои; администратор — все и владельцев. Эти ограничения
в UI иллюстративные: настоящую проверку прав выполняет будущий Go backend.
Список статический, новые песни пока не сохраняются; демо-ссылки не являются
защищёнными токенами и не реализуют отзыв доступа. Состояния: мобильный, админ,
пустой список, поиск без результатов, интерактивный поиск/сортировка,
общий список только для просмотра и редактирование с сохранением в памяти макета.
Кнопка «Ссылка на список» копирует `/?page=library&list=choir-demo`; она открывает
гостевой режим и не передаёт права редактора.

Публикация Pages включает сам макет приложения в `/app/` рядом со Storybook.
Общий список: `https://axepuff.github.io/choral-training-tool/app/?page=library&list=choir-demo`.
После обеих сборок команда `node scripts/assemble-pages.mjs` добавляет приложение
в артефакт Storybook; workflow выполняет её автоматически. Ссылки из Storybook
на песню/создание и копируемые ссылки ведут в этот предпросмотр приложения.
При локальной проверке опубликованной структуры соберите оба проекта, выполните
эту команду и обслуживайте `storybook-static` обычным статическим HTTP-сервером.

Мобильный список использует компактные строки: название открывает плеер, справа
иконки редактирования и ссылки, области касания 44 × 44 px. Поиск и сортировка
расположены в одну строку. Кнопки создания и ссылки на список доступны только
преподавателю/администратору. Story «Длинный список · 360 px» показывает 16 песен
и перенос длинного названия.

Авторизация backend (Issue #4): реальные email/пароль, cookie-сессии, CSRF,
серверные роли, bootstrap/teacher/reset-admin CLI. Настройки и безопасные
операторские команды: [docs/backend.md](docs/backend.md#авторизация-issue-4).
Frontend подключается отдельно в #9; UI и дизайн в этой задаче не менялись.

API песен и дорожек (Issue #5): реальный SQLite CRUD, права владельца/admin,
Unicode validation, If-Match, идемпотентное создание, поиск/сортировка и снимки
списков. Запуск и проверки: [docs/backend.md](docs/backend.md#песни-и-дорожки-issue-5).
Каталог данных теперь также содержит локальный секрет `song-responses.key`: его
нужно сохранять на томе и включать в защищённые резервные копии. Frontend остаётся
макетом; upload, FFmpeg, публичные ссылки и подключение UI — отдельные задачи.

Публичные ссылки (Issue #6): реальные song/list токены, отзыв/ротация, публичные
метаданные и авторизация media с GET/HEAD/Range. Данные аккаунтов и оригиналы
не выдаются. [Контракт, проверки и границы Storage](docs/backend.md#публичные-ссылки-и-media-issue-6).
Файловый адаптер/worker подключаются в #7/#8 (пока без Storage media отвечает 503);
подключение ссылок к существующему UI — #10. Дизайн не изменён.

Issue #7: backend принимает настоящие аудиозагрузки, проверяет FFprobe, сохраняет
приватные originals и durable jobs. UI остаётся макетом, конвертация — следующая
задача #8. Лимиты, запуск, проверки и границы: [docs/backend.md](docs/backend.md#загрузка-и-приватное-хранилище-issue-7).

Issue #8: сервер запускает настоящий SQLite-backed FFmpeg worker (Linux,
`ffmpeg`, `ffprobe`, util-linux `prlimit` обязательны). После upload проверенные
AAC-LC mono/48 kHz и peaks появляются через существующий media API; original
удаляется после commit, failed original и старый playback при замене сохраняются.
Лимиты, retry/recovery, проверенные форматы и ограничение проверки FFmpeg 7.1.x:
[документация worker](docs/backend.md#обработка-аудио-issue-8).

Frontend auth runtime, локальный dev proxy, явный режим демонстрации Pages и

Интеграция списка, формы, загрузки и публичных ссылок с реальным Go API:
